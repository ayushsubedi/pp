Engineering Foundations

"Strong foundations from day 1" only means something if it's a concrete, checkable list — not a value statement. This is that list. Owned jointly by the founder and the Senior Backend Engineer #2 — no dedicated platform hire — built in month 1 before either product pillar.

Source control & review

  • Trunk-based development, short-lived branches — not long-running feature branches that drift and merge painfully
  • No direct pushes to main; every change goes through a pull request
  • Minimum 1 senior approval to merge; 2 approvals for anything touching commission math, e-signature integration, jurisdiction rules, or auth/permissions
  • PR template requires: what changed, why, how it was tested — AI-authored or not

CI pipeline — required to merge, not advisory

  • Lint (formatting + style) fails the build, not just warns
  • Type-check (mypy/pyright for Python, Dart's analyzer for Flutter)
  • Unit tests + integration tests — a defined coverage floor on the two pillars specifically, not just an aggregate number that can hide gaps
  • Dependency/security scanning (e.g. Dependabot or Snyk) on every PR, not a quarterly afterthought
  • Build must succeed for both the API and the Flutter app before merge

Infrastructure

  • Infrastructure as code (Terraform or AWS CDK) — environments are reproducible from a repo, not hand-configured in the console
  • Separate staging and production, with the same IaC deploying both
  • Secrets in AWS Secrets Manager / Parameter Store — never in code, never in plain env files committed anywhere
  • IAM least-privilege from the start, not "make it work, lock it down later"
  • Automated backups with a tested restore process, not just backups nobody's confirmed work

Observability

  • Structured logging (not print statements) from day one
  • Error tracking (e.g. Sentry-equivalent) wired in before the first real user touches the system
  • Basic uptime/health monitoring on every deployed service
  • A place these actually get looked at — alerting to somewhere a human will see it, not a dashboard nobody opens

Multi-tenancy & white-label

Every brokerage in the pilot is a tenant, and the data model needs to isolate them correctly from month 1 — retrofitting tenant isolation into a schema built without it is one of the most expensive mistakes to fix later, on the same "foundations before features" logic as everything else on this page.

  • Row-level tenant isolation (a brokerage_id/tenant column enforced at the query layer, not just application-level convention) rather than a separate database per brokerage — simpler to operate at pilot scale, and the standard pattern for a B2B2C SaaS at this stage
  • Every table that holds brokerage-scoped data carries the tenant key from the first migration, not bolted on after the first real brokerage signs up
  • Auth and permissions are tenant-aware by construction — a user's access is scoped to their brokerage everywhere, not enforced ad hoc per endpoint

White-label is a real question worth asking early, given how the competitive landscape works — Updater and MoveEasy, the closest precedents to RealEZ's own marketplace model, are both white-labeled to brokerages as a client-retention perk. RealEZ isn't building white-label as a Phase 1 feature (the pilot runs under RealEZ's own brand), but the architecture should keep it cheap to add later: branding (logo, colors, sender domain for emails) as tenant-level configuration rather than hardcoded, so flipping it on for a brokerage partner post-pilot is a config change, not a rebuild. This costs very little extra now and a lot more to retrofit once brokerage-specific assumptions are baked into the templates.

Decisions & process

  • Lightweight Architecture Decision Records (ADRs) for anything hard to reverse — database schema for the Transitional Document, the e-sig vendor choice, the commission-ledger design
  • A written incident/postmortem practice, even at this size — what broke, why, what changes so it doesn't happen the same way twice
  • A written AI-usage policy (see Tech Stack for the actual safe/always-human-verified split) that's part of onboarding, not tribal knowledge
Why this is a required deliverable, not a hope: if nobody's explicitly accountable for "make sure this list stays true," it doesn't happen — it either gets skipped under deadline pressure, or gets retrofitted later at several times the cost, usually right after an incident forces the issue. That's why Scenario C makes it the founder's and the Senior Backend Engineer #2's explicit week-1 responsibility rather than assuming it happens alongside feature work — see Team.
