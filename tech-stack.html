How we build

Tech Stack

Language and framework choices, and what "AI-native with human-in-the-loop" actually means day to day, not just as a slogan. AI-native building is the default across every scenario on this site — it's not something only one plan does.

Backend language

OptionProsCons
Python / FastAPI (current)
  • Already built — the POC exists and works
  • Excellent AI-coding-assistant support (heavily represented in training data)
  • Fast to iterate, low ceremony
  • Strong, available talent pool including Nepal
  • Weaker raw throughput than compiled languages at high scale — irrelevant at pilot volume
  • Type safety requires discipline (mypy/pyright), doesn't come for free
Django (Python)
  • Batteries-included — admin panel, ORM, auth out of the box
  • Same Python talent pool and AI-assistant strength as FastAPI
  • Could reduce custom code for Broker/Admin back-office screens
  • More monolithic/opinionated than FastAPI — a real migration, not a drop-in swap, for no functional gain since FastAPI already works
  • Less natural fit for an API-first architecture serving a mobile app as a primary client
Node.js / TypeScript
  • Strong typing by default
  • One language across backend and any future frontend SPA
  • Very strong AI-assistant support
  • Would mean rewriting a working backend for no functional gain right now
  • Async footguns are a real, common source of subtle bugs
Ruby / Rails
  • Mature, convention-over-configuration — historically strong for fast, CRUD-heavy startups
  • Reasonable AI-assistant support
  • Smaller Nepal talent pool than Python/Node
  • Ecosystem momentum has slowed relative to Python/TypeScript in recent years
  • Rewrite cost with no functional gain
Go
  • Excellent performance and concurrency story
  • Simple, hard to write deeply "clever" bad code
  • Rewrite cost with no near-term payoff
  • Slower to prototype in — verbose for CRUD-heavy product work
  • Smaller Nepal talent pool than Python/Node
Rust
  • Best-in-class performance and memory safety
  • Growing ecosystem momentum
  • Steepest learning curve of any option here — slowest to prototype in
  • Smallest Nepal talent pool of all options listed
  • AI-assistant code generation is improving but still lags Python/JS, and the borrow checker punishes half-correct generated code in a way that's a bad match for a lean, fast-moving pilot team
Java / Kotlin
  • Mature ecosystem, strong typing, good for large teams over years
  • Heaviest ceremony of the options here — wrong trade for a lean team validating a pilot
  • Rewrite cost with no near-term payoff
Recommendation

Keep Python/FastAPI. Rewriting working code for hypothetical future scale before product-market fit is a classic, avoidable mistake. Add mypy/pyright to CI (see Foundations) to get real type safety without a rewrite.

Mobile

OptionProsCons
Flutter (current)
  • Already built — existing FTE dev and app shell
  • One codebase for iOS + Android — the only realistic way a single mobile engineer covers both platforms
  • Decent AI-assistant support
  • Occasional platform-specific quirks need native escape hatches
  • Smaller hiring pool than React Native in some markets
React Native
  • Large ecosystem and hiring pool
  • Shares some mental model with a future web SPA, if we ever adopt one
  • Rewrite cost with no functional gain right now
  • Bridge-related performance quirks of its own
Native (Swift + Kotlin, separately)
  • Best possible platform fit and performance
  • Two codebases to build and review — directly conflicts with a single mobile engineer covering both platforms
  • Not remotely justified at pilot scale
Recommendation

Keep Flutter. Same logic as backend — it's built, it works, and a single codebase is what makes one senior mobile engineer, with AI-assisted development, realistically able to cover Agent + Client native parity in a 5-month window without a second hire.

Web frontend

OptionProsCons
Server-rendered Jinja2 + HTMX + Bulma (current)
  • Already built across every portal
  • No build step, no client-state framework to reason about
  • Simpler for AI to generate safely — less room for subtle client-state bugs
  • Less suited to a highly interactive experience if Merchant Integration's marketplace browsing ever needs rich client-side filtering/search
SPA framework (React / Vue)
  • Better fit for rich, highly interactive UI
  • Large talent pool
  • Full rewrite of every existing portal — not defensible before pilot
  • Adds a build pipeline and client-state complexity the team doesn't need yet
Recommendation

Keep the current approach for Broker/Admin/Vendor web. Revisit only if Merchant Integration's marketplace browsing genuinely needs SPA-grade interactivity post-pilot — don't pre-optimize for it now.

How we build: AI-native with human-in-the-loop, everywhere

This isn't one scenario's approach — it's the default across A, B, and C. Every developer has Claude coding access. That's a real velocity multiplier on well-specified, well-scoped work, and part of why the team can stay lean (see Team) — but it's a real risk on anything that touches money or law if it's not paired with deliberate review discipline. The practice, not just the principle:

Safe to AI-generate with light reviewAlways senior-authored or line-by-line human-verified
  • Test scaffolding and test cases following an established pattern
  • CRUD boilerplate, UI screens matching the existing design system
  • Documentation, code comments, migration scripts following a known shape
  • Refactors with full test coverage as a safety net
  • Jurisdiction rules logic (disclosure timing, forms)
  • Commission/payment math and the Merchant Integration ledger
  • E-signature vendor integration, especially webhook/callback handling
  • Auth and permissions logic
  • The Transitional Document's gap-detection logic (it drives real recommendations)

The mechanism that makes this real, not aspirational, is mandatory PR review enforced in CI — see Foundations. "AI wrote it and it looked fine" is not a merge criterion.

Every "keep the current stack" recommendation here rests on the same principle: rewriting working code for a hypothetical future need, before product-market fit, is a cost with no offsetting benefit yet.
